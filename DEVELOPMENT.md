# Local development

## Workspace and source

This repository belongs at `~/workspace/github/infocusmodereal/liquibase-starrocks`,
following the workspace's `github/<owner>/<repository>` layout.
Upstream: https://github.com/infocusmodereal/liquibase-starrocks.

The existing clone was reused and checked against `origin/main`. Local setup

## Requirements

The checked-in build uses JDK 17, Gradle 8.10 (via the wrapper), Kotlin 1.8.0,
Liquibase 5.0.3 and MySQL Connector/J 8.4.0. Use these versions to reproduce
the baseline before attempting dependency upgrades. Internet access is needed
on the first build to download Gradle and dependencies.

On this Mac, JDK 17 is already installed through Homebrew. `scripts/dev` finds
Homebrew's JDK on Apple Silicon or Intel Macs, or a registered macOS JDK 17.
An explicit `JAVA_HOME` takes precedence. On Linux, install JDK 17 and expose
it through `JAVA_HOME` or `PATH`.

## Build and edit

```bash
cd ~/workspace/github/infocusmodereal/liquibase-starrocks
./scripts/dev                  # build and shadowJar, snapshot mode
./scripts/dev test             # run the test task
./scripts/dev clean shadowJar  # rebuild the CLI plugin
./scripts/dev prepareIntegrationJar # exact CLI artifact in build/integration/
./scripts/dev test -PtestLiquibaseVersion=5.0.3 # test against another runtime
```

The helper uses the checked-in wrapper and forces snapshot mode, so ordinary
development builds do not activate release signing. It does not modify shell
profiles or global Java settings. Publishing remains a separate workflow in
`PUBLISHING.md`; do not use the helper for publishing.

Generated JARs live in `build/libs/`. Use the filename generated by your build;
the default version is `0.2.0-SNAPSHOT`, and local properties may override it.
The CLI needs the shadow JAR plus the MySQL JDBC driver.

In IntelliJ IDEA, open this directory as a Gradle project, use the Gradle
wrapper, and set both Project SDK and Gradle JVM to JDK 17. On this Mac its
home is `/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home`.

Implementation is under `src/main/kotlin/liquibase/ext/starrocks/`:

- `database/`: StarRocks recognition and database behavior.
- `sqlgenerator/`: SQL emitted for Liquibase operations.
- `lockservice/`: changelog locking.
- `datatype/` and `params/`: type mapping and table properties.
- `src/main/resources/META-INF/services/`: plugin discovery registrations.

JUnit tests under `src/test/kotlin/` cover lock release and recovery, real
checksum generation, SQL distribution syntax, service discovery and type
mapping. Mockito isolates the executor boundary for lock lifecycle tests;
the Docker tests verify actual database behavior.

## Integration with StarRocks

The existing Compose setup runs StarRocks `3.1.7` and a JDK 17 test runner.
It requires a fresh `liquibase_test` database, applies the changelog, repeats
updates, recalculates and validates checksums, and recovers an abandoned lock
using a new CLI process. The script rejects an existing test database to avoid
a false pass from an earlier run. Recreate the disposable stack between runs.

Prerequisites: a running Docker engine, Compose, available ports 8030 and 9030,
and enough Docker resources for StarRocks. The image's support for your CPU
architecture must be checked when pulling it, especially on Apple Silicon.
Ports bind to localhost; `STARROCKS_SQL_PORT` and `STARROCKS_HTTP_PORT` can
override the host ports. The runner builds from an allowlist in `.dockerignore`
and mounts only `integration/.cache/`, not the checkout or signing files.

```bash
docker compose -p liquibase-starrocks-dev -f docker-compose.integration.yml config --quiet
docker compose -p liquibase-starrocks-dev -f docker-compose.integration.yml up --build --abort-on-container-exit --exit-code-from integration
```

For the newer runtime matrix, use a fresh stack and set:

```bash
STARROCKS_IMAGE=starrocks/allin1-ubuntu:4.1.1 \
INTEGRATION_JAVA_VERSION=21 INTEGRATION_LIQUIBASE_VERSION=4.29.1 \
docker compose -p liquibase-starrocks-dev -f docker-compose.integration.yml up --build --abort-on-container-exit --exit-code-from integration
```

Use `INTEGRATION_LIQUIBASE_VERSION=5.0.3` for the 5.x runtime check.
`EXTENSION_VERSION=0.1.2` selects the published Maven artifact to reproduce
the old lock failure. Leave it unset to exercise the source build. Logging is
explicitly enabled so severe errors cannot be hidden by CLI defaults.
StarRocks 4.1.0 has a documented container startup issue; see `COMPATIBILITY.md`.

For diagnostics:

```bash
docker compose -p liquibase-starrocks-dev -f docker-compose.integration.yml logs starrocks integration
```

To remove only this test stack and its disposable data:

```bash
docker compose -p liquibase-starrocks-dev -f docker-compose.integration.yml down -v
```

Downloads are cached in ignored `integration/.cache/`. Keep credentials and
signing material out of source control. Local builds do not require publishing
credentials; do not copy local credential files into a new checkout.
